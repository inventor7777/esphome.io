The `microchip_atsha204a` component communicates with a Microchip [ATSHA204A][product] over I²C or the
chip's single-wire interface (SWI). It can report chip presence, serial number and revision, and run
the chip's commands from automations. See the [Microchip datasheet][datasheet] for pinouts and electrical specifications.

## Configuration

This example uses the I²C version of the chip and requires an [I²C bus](/components/i2c/) at 100 kHz or
slower. Use a dedicated bus if other devices respond to the general-call address (`0x00`), which the
component uses to wake the chip.

```yaml
microchip_atsha204a:
  transport: i2c
```

### Configuration Variables

- **transport** (**Required**, string): One of `i2c`, `swi_rmt`, or `swi_uart`.
- **id** (*Optional*, [ID](/guides/configuration-types/#id)): The ID of this hub.
- **update_interval** (*Optional*, [Time](/guides/configuration-types/#time)): How often to check for the
  chip and read its identity. Defaults to `never`. Set an interval to update the entities automatically, or
  use [`component.update`](/automations/actions/#component-update-action) to poll on demand.

### I²C Transport

- **i2c_id** (*Optional*, [ID](/guides/configuration-types/#id)): The I²C bus to use.
- **address** (*Optional*, int): The chip's 7-bit address. Defaults to `0x64`.

### Single-Wire RMT Transport

Use `transport: swi_rmt` on an original ESP32 with ESP-IDF 5.5.4 or newer. This transport uses one
RMT transmit channel and exclusive use of UART2. It requires a pull-up on the signal wire.

```yaml
microchip_atsha204a:
  transport: swi_rmt
  pin: GPIOXX
```

- **pin** (**Required**, [Pin Schema](/guides/configuration-types/#pin-schema)): The non-inverted
  GPIO connected to the signal wire. Choose a pin other than GPIO16, the dedicated UART2 RX pin.
- **rmt_symbols** (*Optional*, int): The RMT memory allocation. The original ESP32 uses one
  block of 64 symbols.

### Single-Wire UART Transport

Use `transport: swi_uart` with a dedicated [hardware UART](/components/uart/) at 230400 baud, 7 data
bits, no parity and 1 stop bit. Set `rx_buffer_size` to at least 680 bytes. Connect RX to the
pulled-up signal. Connect TX through a low-forward-voltage Schottky diode with the anode at the signal
and the cathode at TX, or through an equivalent open-drain buffer.

```yaml
microchip_atsha204a:
  transport: swi_uart
  wake_pin:
    number: GPIOXX
    mode:
      output: true
      open_drain: true
```

- **uart_id** (*Optional*, [ID](/guides/configuration-types/#id)): The UART bus to use.
- **wake_pin** (**Required**, [Pin Schema](/guides/configuration-types/#pin-schema)): A non-inverted,
  open-drain GPIO output connected to the signal wire.

## Presence and Identity

The binary sensor reports whether the chip is present. The text sensors report uppercase hexadecimal
values and publish an empty string when the chip is removed.

```yaml
binary_sensor:
  - platform: microchip_atsha204a
    name: "Chip Present"

text_sensor:
  - platform: microchip_atsha204a
    serial_number:
      name: "Chip Serial Number"
    chip_revision:
      name: "Chip Revision"
```

- **atsha204a_id** (*Optional*, [ID](/guides/configuration-types/#id)): The hub to use. This option
  is available on both platforms.
- **serial_number** (*Optional*): The chip's 9-byte serial number. All options from
  [Text Sensor](/components/text_sensor/).
- **chip_revision** (*Optional*): The chip's 4-byte silicon revision. All options from
  [Text Sensor](/components/text_sensor/).

All other options from [Binary Sensor](/components/binary_sensor/) apply to the presence sensor.

## `microchip_atsha204a.command` Action

This action sends an opcode and its arguments. See the [datasheet][datasheet] for each command's
parameter and data encodings. The automation continues after issuing the request. Use `on_result`
for steps that need the reply. Polling is suspended while a command or session is active. Set `id: chip`
on the hub to use the following example.

```yaml
- microchip_atsha204a.command:
    id: chip
    opcode: dev_rev
    on_result:
      - lambda: |-
          if (status == 0 && data.size() == 4) {
            ESP_LOGI("atsha204a", "Revision %02X%02X%02X%02X", data[0], data[1], data[2], data[3]);
          }
```

- **id** (**Required**, [ID](/guides/configuration-types/#id)): The hub to use.
- **opcode** (**Required**, string): One of `check_mac`, `derive_key`, `dev_rev`, `gen_dig`, `hmac`,
  `lock`, `mac`, `nonce`, `pause`, `random`, `read`, `sha`, `update_extra`, or `write`.
- **param1** (*Optional*, int, [templatable](/automations/templates/)): An 8-bit parameter. Defaults to `0`.
- **param2** (*Optional*, int, [templatable](/automations/templates/)): A 16-bit parameter. Defaults to `0`.
- **data** (*Optional*, list, [templatable](/automations/templates/)): Up to 77 bytes of command data.
  A lambda returns a `std::vector<uint8_t>`. Defaults to an empty list.
- **end** (*Optional*, string): `sleep` clears the chip's temporary state and releases the session.
  `keep_awake` leaves the chip awake. `idle` retains chip state as described in the datasheet and
  wakes the chip for the next command. Defaults to `sleep`.
- **session** (*Optional*, int, [templatable](/automations/templates/)): The token returned by a
  previous command. Use `session: !lambda return session;` from its `on_result` automation. Defaults to `0`
  to start a new session.
- **expect_response** (*Optional*, boolean): Defaults to `true`. Set to `false` for a `pause` command
  with `end: sleep` when the chip is expected to enter idle without replying.
- **on_result** (*Optional*, [Automation](/automations/)): Runs on completion and receives
  `status` (0 for success, a positive chip status code, or a negative driver error), `data`
  (the reply payload as a byte sequence), and `session` (0 unless the session is still open).

| Status | Driver error |
| --- | --- |
| `-1` | Busy |
| `-2` | Response timed out |
| `-3` | Response CRC mismatch |
| `-4` | Invalid response framing or length |
| `-5` | Transport error |
| `-6` | Invalid or expired session |
| `-7` | Invalid command arguments |
| `-8` | Unexpected wake status |

A session expires after 500 ms without a follow-up. The chip's watchdog also limits how long it can
remain awake. On a shared single-wire bus, use a `pause` command to select the chip and
`keep_awake` to retain that selection for follow-up commands.

A successful `lock` permanently locks the selected zone. Some writes to the one-time programmable
zone are irreversible. If a write response is lost, read back the affected state before issuing
the command again.

## `microchip_atsha204a.end_session` Action

Put the chip to sleep and release an open session before it expires.

- **id** (**Required**, [ID](/guides/configuration-types/#id)): The hub to use.
- **session** (**Required**, int, [templatable](/automations/templates/)): The token returned by
  `microchip_atsha204a.command`.

## C++ API

The hub exposes `command()` and `end_session()` for C++ integrations. A polling integration can
register a callback with `set_poll_callback()` and chain reads with `read_block()` from that callback
or its completion callback. The block pointer is valid only for the duration of the completion
callback and is null on a failed response. Use `set_disconnect_callback()` to clear data when the
chip is removed.
